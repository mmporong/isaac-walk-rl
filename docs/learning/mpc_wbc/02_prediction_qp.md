# 02. Prediction부터 QP와 Receding Horizon까지

- 대응 원문: [Centroidal MPC Prediction부터 OSQP까지 - M·S·d, Q/R, Constraint, Receding Horizon](https://app.notion.com/p/Centroidal-MPC-Prediction-OSQP-M-S-d-Q-R-Constraint-Receding-Horizon-3cace2d5e06081a1a9e6c85d98930ff3?pvs=25)
- 원문 대응 범위: 1~27절과 마지막 6단계 복습 순서
- 선수 지식: [`01_centroidal_dynamics.md`](01_centroidal_dynamics.md)의 `x_next=Ax+Bu+c`
- 학습 목표: 한 스텝 동역학을 미래 전체로 펼치고, 목표·비용·제약을 합쳐 QP로 푸는 이유를 설명한다.

## 먼저 한 문장

MPC는 가능한 미래 발 힘들을 여러 스텝 앞까지 시험해보고, 목표를 잘 따라가면서도 힘을 낭비하지 않고 미끄러지지 않는 계획을 고른 뒤 첫 힘만 사용한다.

```text
미래 예측 -> 좋은 계획의 기준 -> 물리 제약 -> 최적화 -> 첫 입력 실행 -> 다시 계산
```

## 1. 왜 한 스텝만 보면 부족한가

현재 자세만 바로잡으려고 힘을 크게 쓰면 다음 순간 발이 미끄러지거나 곧 support가 사라질 수 있다. MPC는 미래 `N`개 timestep의 상태와 발 힘을 함께 본다.

한 스텝 모델은:

```text
x[k+1] = A · x[k] + B · u[k] + c
```

두 스텝 앞은 첫 식을 다시 대입해서 얻는다.

```text
x[k+2] = A²·x[k] + A·B·u[k] + B·u[k+1] + A·c + c
```

세 스텝, 네 스텝도 같은 방식으로 펼칠 수 있지만 매번 손으로 전개하기 어렵다. 그래서 큰 행렬 `M`, `S`, `d`로 묶는다.

## 2. 미래 전체를 한 식으로 묶기

미래 상태와 입력을 세로로 쌓는다.

```text
X = [x₁, x₂, ..., x_N]을 세로로 쌓은 미래 상태 묶음
U = [u₀, u₁, ..., u_(N-1)]을 세로로 쌓은 미래 입력 묶음
```

그러면 prediction 식은 다음 하나로 정리된다.

```text
X = M · x₀ + S · U + d
```

| 기호 | 쉬운 뜻 |
|---|---|
| `Mx_0` | 지금 상태를 그대로 두면 미래에 어떻게 퍼지는가 |
| `SU` | 각 시점의 발 힘이 이후 미래 상태를 어떻게 바꾸는가 |
| `d` | 매 timestep 들어오는 중력이 미래에 얼마나 누적되는가 |

### `M`: 현재 상태의 미래 전파

```text
M = [A, A², ..., Aᴺ]을 세로로 쌓은 행렬
```

`A^3x_0`는 현재 상태가 세 번의 자연 진행을 거친 결과다.

### `S`: 미래 힘의 영향표

`u_0`는 첫 스텝부터 작용하므로 많은 미래 상태에 영향을 준다. 마지막 입력 `u_{N-1}`은 마지막 상태에만 영향을 준다. 그래서 `S`는 아래쪽으로 채워지는 block-lower-triangular 형태다.

```text
S = [ B           0       ...   0 ]
    [ A·B         B       ...   0 ]
    [ ...         ...     ... ... ]
    [ Aᴺ⁻¹·B   Aᴺ⁻²·B    ...   B ]
```

### `d`: 중력의 누적

첫 미래에는 `c`, 두 번째 미래에는 `Ac+c`, 세 번째에는 `A^2c+Ac+c`가 들어간다. `d`는 이것들을 세로로 쌓은 벡터다.

## 3. Reference: 어떤 미래를 원하는가

예측만으로는 좋은 미래인지 나쁜 미래인지 판단할 수 없다. 원하는 미래 상태를 `X_ref`로 둔다.

예:

- 몸통 높이 유지
- roll과 pitch를 0에 가깝게 유지
- 명령한 전진 속도 추종
- 명령한 yaw rate 추종

Reference의 구체적인 생성 방법은 [`03_reference_generator.md`](03_reference_generator.md)에 있다.

## 4. `Q`와 `R`: 무엇을 얼마나 중요하게 볼 것인가

상태 추적 오차와 힘 사용량을 함께 비용으로 둔다.

```text
비용 J = (X - X_ref)ᵀ · Q_bar · (X - X_ref)
       + Uᵀ · R_bar · U
```

### `Q`: 상태 추적 중요도

`Q`가 큰 상태는 목표에서 벗어날 때 비용이 크게 증가한다.

- 높이 가중치가 크다: 몸통 높이를 강하게 지킨다.
- roll/pitch 가중치가 크다: 몸통 기울기를 강하게 바로잡는다.
- 속도 가중치가 작다: 명령 속도 오차를 어느 정도 허용한다.

### `R`: 입력 사용 비용

`R`가 크면 큰 발 힘이나 급격한 힘 사용을 꺼린다. 너무 작으면 목표는 잘 따라도 비현실적으로 큰 힘을 요구할 수 있고, 너무 크면 힘을 아끼느라 목표를 놓친다.

`Reference`는 어디로 갈지를 정하고, `Q/R`은 무엇을 얼마나 중요하게 볼지를 정한다.

## 5. QP 형태로 바꾸기

Prediction을 비용식에 넣고 `U`에 관계없는 상수를 제외한다. 먼저:

```text
e = M · x₀ + d - X_ref
```

라 두면:

```text
X - X_ref = S · U + e
```

한 가지 일반적인 표준형은:

```text
U에 대해 최소화:  0.5 · Uᵀ · P · U + qᵀ · U
```

이며 다음처럼 구성할 수 있다.

```text
P = 2 · (Sᵀ · Q_bar · S + R_bar)
q = 2 · Sᵀ · Q_bar · e
```

- `P`: 입력끼리의 이차 관계와 곡률
- `q`: 현재 오차가 어느 방향의 힘을 요구하는지 나타내는 선형 항
- 결정변수 `U`: horizon 전체의 네 발 힘

이런 이차 목적함수와 선형 제약을 가진 문제를 Quadratic Program, QP라고 한다.

## 6. 왜 제약이 필요한가

비용만 최소화하면 수학적으로는 큰 수평력을 사용해 목표를 빨리 따라갈 수 있다. 하지만 실제 발은 바닥을 당길 수 없고 마찰보다 큰 수평력을 만들면 미끄러진다.

### 수직력 제약

stance 발에는 허용 가능한 수직력 범위가 있다.

```text
f_min ≤ f_z ≤ f_max
```

### 마찰 제약

마찰원 또는 마찰원뿔을 계산하기 쉬운 선형 피라미드로 근사한다.

```text
-mu·f_z ≤ f_x ≤ mu·f_z
-mu·f_z ≤ f_y ≤ mu·f_z
```

수직력이 작으면 사용할 수 있는 수평력도 작아진다.

### Swing 발 제약

공중에 있는 발은 바닥을 밀 수 없다.

```text
공중에 있는 발의 힘 F_swing = 0
```

따라서 gait schedule이 미래 각 스텝에서 어떤 발을 stance와 swing으로 볼지 알려줘야 한다.

## 7. Solver가 실제로 찾는 것

OSQP 같은 QP solver는 다음을 동시에 만족하는 `U`를 찾는다.

1. 몸통의 미래 상태가 reference를 잘 따라간다.
2. 발 힘을 지나치게 쓰지 않는다.
3. 수직력과 마찰 제약을 지킨다.
4. swing 발의 힘을 0으로 둔다.

Notion은 OSQP를 설명하지만 Cheetah 3 원 논문은 qpOASES를 사용한다. 특정 solver는 알고리즘의 필수 정답이 아니다.

## 8. 첫 번째 입력만 쓰는 이유

최적화 결과는 미래 힘 계획 전체다.

```text
최적 미래 입력 U* = [u₀*, u₁*, ..., u_(N-1)*]
```

하지만 실제로는 `u_0^*`만 적용한다. 그 사이 로봇은 움직이고 센서로 새 상태를 얻는다. 이전 계획의 나머지를 그대로 믿기보다 새 상태에서 다시 최적화한다.

```text
측정 x_k
  -> 미래 N스텝 최적화
  -> 첫 힘 u_0만 적용
  -> 새 상태 x_{k+1} 측정
  -> 다시 미래 N스텝 최적화
```

이 반복을 Receding Horizon이라고 한다. 모델 오차와 외란을 매 주기 새 측정으로 보정하는 구조다.

## 9. Warm Start와 실패 대응

### Warm Start

이전 최적해를 한 칸 앞으로 밀어 다음 solver의 초기값으로 사용한다.

```text
다음 초기값 = [u₁*, u₂*, ..., u_(N-1)*, u_(N-1)*]
```

연속된 제어 주기에서는 최적해가 갑자기 크게 달라지지 않는 경우가 많아 계산 시간을 줄일 수 있다.

### 실패 대응

solver는 infeasible, timeout 또는 수치 문제로 실패할 수 있다. 이때 실패한 벡터를 그대로 관절에 보내면 안 된다. 간단한 standing fallback의 예는 stance 발 `n`개가 무게를 나누는 것이다.

```text
stance 발 i의 수직력 ≈ m·g / stance 발 개수
```

실제 구현에서는 마지막 유효해 유지 시간, force clipping, 안전 자세 전환과 실패 횟수 기록까지 계약으로 정해야 한다.

## 10. 힘을 관절 토크로 내리기

MPC가 구한 stance 발의 world-frame 힘은 필요한 frame으로 회전한 뒤 Jacobian transpose로 관절 토크에 연결한다.

```text
관절 토크 tau_i = J_iᵀ · R_iᵀ · 발 힘 f_i
```

swing 발은 MPC의 stance GRF 대신 별도의 Cartesian trajectory와 PD/feedforward 제어를 사용한다.

## 11. 작은 차원 예시

12차원 대신 위치와 속도만 있는 1차원 모델을 생각한다.

```text
p[k+1] = p[k] + v[k]·dt + (dt² / 2m)·F[k]
v[k+1] = v[k]           + (dt / m)·F[k]
```

`N=3`이면 solver는 `[F_0,F_1,F_2]`를 고른다. `F_0`는 세 미래 상태에, `F_2`는 마지막 미래 상태에만 영향을 준다. 이것이 `S`가 아래쪽 삼각형 모양이 되는 이유다.

## 수치를 복사하면 안 되는 이유

Notion의 QUATTRO 예시는 `N=12`, `dt=0.02s`, 약 `0.24s` horizon과 OSQP를 사용한다. Cheetah 3 논문은 `0.33~0.5s`, 10~16 timestep과 qpOASES를 보고한다. 현재 Go2의 질량·제어주기·접촉·solver 예산을 측정하지 않고 어느 쪽도 그대로 사용하지 않는다.

## 확인 문제

1. `X=Mx_0+SU+d`에서 `M`, `S`, `d`를 말로 설명한다.
2. `Q`를 크게 하는 것과 `R`을 크게 하는 것의 차이를 설명한다.
3. 마찰 제약에서 `f_z`가 작아지면 허용 수평력은 어떻게 되는가?
4. swing 발의 GRF를 왜 0으로 고정하는가?
5. 미래 입력 전체를 풀면서 첫 입력만 적용하는 이유는 무엇인가?
6. solver가 실패했을 때 필요한 안전 계약을 두 가지 적는다.

### 최소 통과 기준

다음 흐름을 자료 없이 말할 수 있으면 된다.

```text
한 스텝 모델을 horizon으로 쌓는다
-> reference와 Q/R로 비용을 만든다
-> 접촉과 마찰 제약을 건다
-> QP를 푼다
-> 첫 힘만 적용하고 다시 측정한다
```
